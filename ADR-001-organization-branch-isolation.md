## 1. Context

### 1.1. Что было

До версии 2.2 верхней бизнес-границей системы являлась **Category** — учебное направление (C#, Python, Frontend, Design). Модель данных версии 2.1 содержала:

- `User.CategoryId` — обязателен для Lead и Mentor, `NULL` для Admin;
- `Assignment.CategoryId` — immutable snapshot категории;
- EF Core Global Query Filter по `CategoryId`;
- четырёхуровневую модель изоляции: Category → Ownership → Role → Resource-state;
- ровно одну роль `Admin`, видящую **все** категории и все административные данные системы.

Сущностей `Organization`, `Branch`, полей `OrganizationId`, `BranchId` и понятия `AdminScope` в модели **не существовало**.

### 1.2. Что изменилось в требованиях

Продукт должен обслуживать IT-академию с **несколькими филиалами**: главный офис и региональные подразделения. Каждый филиал ведёт собственные учебные направления с собственными тимлидами, менторами, расписанием и задачами. Направления с одинаковым названием («C#» в главном офисе и «C#» в филиале Худжанд) являются разными учебными потоками без общих данных. Требуется отдельный администратор каждого филиала и сводная аналитика по всей организации.

### 1.3. Почему изоляции по Category оказалось недостаточно

Category — это **предметная**, а не **арендная** граница. Отсутствие уровня выше неё приводит к тому, что при добавлении второго филиала в существующую модель смешиваются:

| Область | Механизм смешения |
|---|---|
| Пользователи | `GET /users` для Admin возвращает всех пользователей системы; фильтра по филиалу не существует |
| Категории | Уникальность имени категории была **глобальной** (`ux_categories_name_lower`) — второй филиал физически не смог бы создать собственную категорию «C#» |
| Расписание | `Topic` и `TopicAssignment` наследуют scope только от Category; Lead одного филиала видит расписание одноимённой категории другого |
| Задания и сдачи | `Assignment.AssignedToId` проверялся на совпадение `CategoryId`, но не филиала; при одноимённых категориях FK не различает менторов разных филиалов |
| Проверки | `Review.ReviewerId` — Lead «той же CategoryId»; при слиянии категорий проверку мог бы вынести Lead чужого филиала |
| Аналитика | Группировка по `Category` объединила бы показатели несвязанных учебных потоков |
| AI-резюме | `CacheKey` не содержал филиала — отчёт одного филиала возвращался бы из кэша для другого |
| Уведомления | `DeduplicationKey` не содержал филиала — уведомление одного филиала **молча подавляло** бы одноимённое уведомление другого |
| AuditLog | Единственная роль Admin видит журнал всей системы, включая действия чужих филиалов |
| Файлы | `StorageKey = submissions/{categoryId}/…` — при одноимённых категориях префиксы неразличимы операционно |
| Фоновые задачи | Планировщик и BDA выбирают менторов «активной категории» без ограничения филиалом |
| Административные операции | Единственный Admin выполняет операции над любыми данными без контура |

Ключевое наблюдение: **все перечисленные дефекты возникают не из-за ошибок реализации, а из-за отсутствия носителя арендного контекста в модели данных.** Ни один из них не может быть устранён проверкой в коде приложения, потому что проверять нечего — филиал не является атрибутом ни одной строки.

### 1.4. Требование к решению

Изоляция филиалов — **граница безопасности**, а не UI-фильтр. Она должна обеспечиваться на уровнях: доменной модели, ограничений PostgreSQL, EF Core, authorization, JWT claims, API, frontend, файлового хранилища, фоновых задач, аналитики и тестов. Отказ любого одного уровня не должен приводить к утечке.

Ограничения, заданные до принятия решения: сохраняются один модульный монолит, один ASP.NET Core API, одна PostgreSQL, одна схема БД, один MinIO, один React SPA. Жизненный цикл Assignment, правила Submission и Review, политика дедлайнов, механика Outbox и flow аутентификации не переписываются.

## 2. Decision

### 2.1. Organization как корень арендности

Вводится сущность **`Organization`** — самая верхняя tenant-граница, представляющая отдельную IT-академию или компанию (ТЗ 10.17).

- `OrganizationId` присутствует **у всех** пользователей без исключения, включая администраторов, и во всех tenant-scoped данных.
- `OrganizationId` **никогда** не принимается от пользователя: значение всегда берётся из аутентифицированного principal (`ORG-021`, `TEN-030a`).
- Ни один пользователь Organization A не видит существования Organization B: ни в списках, ни в счётчиках, ни в поиске, ни в сообщениях об ошибках (`ORG-022`).
- В Release 1.0 Organization создаётся **только** provisioning-процессом; публичного API создания не существует (`ORG-001`, `ORG-002`).
- Один аккаунт принадлежит ровно одной Organization; перевод между Organization не поддерживается (`ORG-023`).
- Физическое удаление запрещено; применяется деактивация (`ORG-006`).

`OrganizationSettings` **не вводится**: настроек уровня всей организации в текущем scope не существует, а пустая сущность немедленно стала бы местом ошибочного размещения branch- и category-настроек (`ORG-024`).

### 2.2. Branch как операционная граница изоляции

Вводится сущность **`Branch`** — филиал внутри Organization (ТЗ 10.18).

Итоговая иерархия:

```
Organization
└── Branch
    └── Category
        ├── CategorySettings, Lead, Mentor
        ├── Topic, TopicAssignment
        ├── Assignment, Submission, Review
        ├── TaskEvent, NotificationOutbox
        └── Analytics
```

- Branch принадлежит ровно одной Organization; `OrganizationId` immutable (`BRN-020`).
- Уникальность `Code` и `NormalizedName` — **в пределах Organization**, не глобально (`BRN-023`).
- Физическое удаление запрещено; применяется деактивация (`BRN-022`).
- `TimeZoneId` валидируется по базе IANA tzdata и служит значением по умолчанию для новых `CategorySettings`; его изменение **не** пересчитывает существующие настройки (`BRN-010`, `BRN-011`, `BRN-029`).

**Главный офис не является специальным техническим контуром.** Это обычный Branch с `IsHeadOffice = true`; на одну Organization приходится ровно один такой филиал, что обеспечивается partial unique index `ux_branches_single_head_office`, а не сервисной проверкой (`BRN-021`, `BRN-040`, `BRN-041`). Флаг влияет ровно на три вещи: отображение в branch selector, выбор часового пояса для отчётов уровня Organization и запрет деактивации до передачи признака другому филиалу. Никаких дополнительных прав доступа он не даёт.

Категории с одинаковым названием в разных филиалах — **разные сущности** без общих пользователей, задач, файлов, уведомлений и аналитики (`TEN-002a`, `CAT-021`).

### 2.3. Shared database / shared schema

Принята модель **одной базы данных и одной общей схемы** для всех арендаторов (ТЗ 38.2):

| Свойство | Решение |
|---|---|
| База данных | Одна PostgreSQL |
| Схема | Одна общая; схема на арендатора не создаётся |
| Идентификаторы | Глобально уникальные UUID v7 |
| Арендные колонки | Прямые `OrganizationId` и `BranchId` |
| ORM | EF Core Global Query Filters |
| Application | Явная scope-проверка в каждом handler |
| Ограничения БД | Composite unique keys, composite FK, CHECK, tenant-ведущие индексы |

### 2.4. Прямые OrganizationId и BranchId

`OrganizationId` и `BranchId` добавляются **непосредственно** в: `Category`, `CategorySettings`, `Topic`, `TopicAssignment`, `Assignment`, `Submission`, `Review`, `TaskEvent`, `NotificationOutbox`, `AuditLog`, `AiSummary`, `UserCategoryHistory`, `UserBranchHistory`, `User` (ТЗ 10.20, Приложение M).

Денормализация принята осознанно: альтернатива — вычисление филиала через цепочку `Submission → Assignment → Category → Branch` — потребовала бы join в каждом запросе, сделала бы невозможным индекс с ведущим `branch_id` и, главное, не позволила бы выразить cross-scope запрет средствами FK.

`BranchId` допускается `NULL` **ровно в трёх** случаях, каждый из которых относится к действию уровня организации: Organization-level AuditLog, Organization-level system alert в Outbox, Organization aggregate AI summary (`TEN-010`). Расширение списка требует изменения ТЗ.

`OrganizationId` и `BranchId` являются **immutable snapshot scope**: при переводе пользователя между филиалами ранее созданные Assignment, Submission, Review, TaskEvent, AuditLog и Outbox сохраняют исходные значения. Исторические данные не переносятся (`TEN-018`, `BRN-049`).

### 2.5. Composite constraints

Введены composite unique keys (`ux_*_id_scope`) и **21 composite FK**, делающие cross-scope связь физически невозможной (ТЗ 12.1a, 12.2a). Ключевые:

| Ограничение | Что становится невозможным |
|---|---|
| `fk_users_category_scope` | Lead/Mentor филиала A, привязанный к категории филиала B |
| `fk_assignments_assignee_scope` | Назначение Assignment на Mentor другого филиала или другой категории |
| `fk_assignments_assigner_scope` | `AssignedById` — Lead другой категории или филиала |
| `fk_reviews_reviewer_scope` | Review, созданный Lead другого филиала |
| `fk_submissions_assignment_scope` | Submission со scope, отличным от Assignment |
| `fk_task_events_assignment_scope` | TaskEvent со scope, отличным от Assignment |
| `fk_topic_assignments_topic_scope` | TopicAssignment, привязанный к Topic другого филиала |

Для отношений, не выразимых обычным FK, применяется **сочетание** composite FK + CHECK + domain validation + transaction validation + integration test; ни один механизм не является достаточным по отдельности (`TEN-022`, `TEN-023`, Приложение M.3).

Нарушение возвращает **409 `CROSS_SCOPE_REFERENCE`** и фиксируется метрикой, рост которой классифицирован как Critical: в корректной системе счётчик обязан оставаться нулевым.

### 2.6. Отказ от PostgreSQL Row Level Security в Release 1.0

RLS **не используется** (`TEN-030`). Обоснование:

1. Приложение уже применяет EF Core Global Query Filters и явные scope-проверки в каждом handler — RLS дублировал бы, но не заменял их.
2. RLS требует передачи арендного контекста через session-переменные (`SET LOCAL`). При использовании пула соединений это превращается в обязательный сброс контекста при каждом возврате соединения в пул; единственная ошибка сброса даёт утечку между арендаторами. Вносимый эксплуатационный риск выше устраняемого.
3. Изоляция дополнительно обеспечивается composite FK и integration-тестами, выполняющими прямые запросы к БД в обход приложения (`TEST-TEN-040`). Эти механизмы работают независимо от роли подключения.
4. Три роли БД с непересекающимися правами (`app`, `migrator`, `retention`) уже ограничивают поверхность доступа.

RLS остаётся кандидатом на будущий hardening. Его введение **не потребует изменения доменной модели**: колонки `organization_id` и `branch_id` уже присутствуют физически. Это осознанное свойство выбранной схемы (`TEN-031`).

### 2.7. Три роли и AdminScope

Сохраняются **ровно три** значения `Role`: `Admin`, `Lead`, `Mentor`. Новые роли (`SuperAdmin`, `HeadOfficeAdmin`, `BranchAdminRole`, `OrganizationAdminRole`) **не создаются** (`TEN-011`).

Для `Role='Admin'` вводится `AdminScope ∈ {Organization, Branch}`:

| Тип | Role | AdminScope | OrganizationId | BranchId | CategoryId |
|---|---|---|---|---|---|
| Organization Admin | `Admin` | `Organization` | NOT NULL | NULL | NULL |
| Branch Admin | `Admin` | `Branch` | NOT NULL | NOT NULL | NULL |
| Lead | `Lead` | NULL | NOT NULL | NOT NULL | NOT NULL |
| Mentor | `Mentor` | NULL | NOT NULL | NOT NULL | NOT NULL |

Допустимы ровно эти четыре сочетания; иные запрещены CHECK-ограничениями `ck_users_scope_shape`, `ck_users_role_admin_scope`, `ck_users_role_category` (`USER-023`).

Разрешено несколько активных Organization Admin в организации и несколько активных Branch Admin в филиале: единственный администратор является единой точкой отказа при потере доступа (`TEN-016`). Ограничение «не более одного активного» сохраняется только для Lead и только в пределах Category.

**Branch Admin не может создать другого Branch Admin** — только Organization Admin (`USER-031`). Самовоспроизводство административного контура филиала лишило бы организацию контроля над составом администраторов.

**Branch Admin имеет только `GET` по своему филиалу**; редактирование Branch доступно только Organization Admin (`BRN-002`, `BRN-008`). Отдельный список филиалов Branch Admin не видит: перечень филиалов раскрывает состав организации.

### 2.8. Шесть уровней изоляции и явный scope-контекст

Четырёхуровневая модель заменена **шестиуровневой** с обязательным порядком проверок (ТЗ 9.1):

```
1. Organization isolation   → 404 RESOURCE_NOT_FOUND
2. Branch isolation         → 404 RESOURCE_NOT_FOUND
3. Category isolation       → 404 RESOURCE_NOT_FOUND
4. Ownership isolation      → 404 RESOURCE_NOT_FOUND
5. Role / AdminScope        → 403 FORBIDDEN | SCOPE_OVERRIDE_FORBIDDEN
6. Resource-state           → 409
```

Чужая Organization, чужой Branch, чужая Category, чужой объект Mentor и несуществующий объект возвращают **побайтово идентичный** 404. Коды вида `FOREIGN_BRANCH` в каталоге отсутствуют намеренно: они подтверждали бы существование объекта за границей видимости (`TEN-006`).

Контекст выполнения формализован двумя абстракциями: `ICurrentUserContext` (данные principal) и `IBranchContext` (вычисленный effective scope). `EffectiveOrganizationId` всегда берётся из principal и не может быть изменён ни одним входным параметром.

Выбор филиала для Organization Admin выполняется заголовком **`X-MTF-Branch-Id`**:

- Branch Admin, Lead и Mentor **не отправляют** заголовок; его наличие → 403 `SCOPE_OVERRIDE_FORBIDDEN` даже при передаче собственного идентификатора;
- Organization Admin: заголовок обязателен для branch-scoped мутаций (иначе 400 `BRANCH_CONTEXT_REQUIRED`), опционален для разрешённых агрегирующих `GET`;
- значение обязано принадлежать Organization пользователя; чужой филиал → 404, не 403;
- **мутация в режиме «Все филиалы» запрещена всегда** (`TEN-034`).

Global Query Filter **не считается единственной защитой**: он отключается вызовом `IgnoreQueryFilters()`, не применяется к сырому SQL и не защищает запись. Каждый handler обязан содержать явную scope-проверку, что контролируется архитектурными тестами `TEST-SEC-021` и `TEST-SEC-022`.

### 2.9. Одно SPA

Сохраняется **одно** React SPA и существующие маршруты `/admin/*`, `/lead/*`, `/mentor/*`. Маршруты `/organization-admin/*`, `/branch-admin/*`, `/head-office-admin/*`, `/branch-N/*` **не создаются** (`FE-030`). Оба администратора работают в разделе `/admin/*`; различие определяется парой `role='Admin'` и `adminScope`, полученной из `/auth/me`.

Вводится клиентский `BranchContext` и branch selector для Organization Admin. `BranchContext` **не является authorization boundary**: он определяет только отправляемый заголовок, ключи кэша и отображение. Его изменение через DevTools не даёт доступа ни к одному чужому объекту (`FE-034`, `FE-045`).

## 3. Consequences

### 3.1. Положительные

1. **Изоляция филиалов обеспечена на семи независимых уровнях** — модель, БД, ORM, application, authorization, API, frontend. Отказ любого одного уровня не приводит к утечке: cross-scope запись отклоняется PostgreSQL даже при полностью обойдённом приложении (`TEST-TEN-040`).
2. **Cross-scope связь физически невозможна**, а не «запрещена правилами». 21 composite FK превращает целый класс потенциальных дефектов в ошибку внешнего ключа на этапе интеграционного теста.
3. **Ни одной новой роли.** Матрица прав не удвоилась: `AdminScope` выражает административный контур одним полем, а не дублированием всей модели авторизации.
4. **Инфраструктура не усложнилась.** Один процесс, одна БД, один бакет, один SPA, один Hangfire. Стоимость эксплуатации не зависит от числа филиалов.
5. **Расширение организации — продуктовая операция.** Создание филиала выполняется Organization Admin через UI и не требует ни деплоя, ни изменения конфигурации, ни вмешательства эксплуатации.
6. **История неизменна.** Immutable snapshot scope гарантирует, что перевод пользователя между филиалами не искажает аналитику ни одного из них задним числом.
7. **Путь к RLS открыт.** Будущее введение Row Level Security не потребует изменения схемы: необходимые колонки уже существуют.
8. **Аудит и наблюдаемость арендно-осведомлены.** Каждая запись AuditLog, каждая запись Outbox и каждая метрика содержат арендный контекст, что делает возможным расследование инцидента изоляции.

### 3.2. Отрицательные

1. **Схема БД усложнилась.** Добавлены 2–3 колонки в 14 таблиц, 13 composite unique index, 21 composite FK, 11 CHECK-ограничений. Каждая новая таблица потребует того же набора — это постоянная налоговая нагрузка на разработку.
2. **Composite unique index `ux_*_id_scope` существуют только как цель FK.** Они не используются для поиска и занимают место и время записи. Накладные расходы приняты осознанно: это единственный способ выразить cross-scope запрет средствами PostgreSQL без триггеров.
3. **Денормализация требует дисциплины.** `OrganizationId`/`BranchId` копируются вниз по иерархии; ошибка копирования даёт рассогласование. Митигация — composite FK, которые делают рассогласованную строку невставляемой, и тест `TEST-TEN-040`.
4. **Каждый handler обязан содержать явную scope-проверку.** Это дублирует Global Query Filter и увеличивает объём кода. Митигация — архитектурные тесты, отклоняющие handler без фильтра.
5. **Общая инфраструктура означает общий blast radius.** Отказ PostgreSQL или MinIO затрагивает все филиалы всех организаций одновременно. Соответствует заявленным SLO (99.5%, RTO 4 ч), но исключает арендно-независимую доступность.
6. **Восстановление отдельного филиала невозможно самообслуживанием.** Backup общий; частичное восстановление требует ручного разрешения конфликтов FK (`TEN-092`).
7. **«Шумные соседи» не изолированы.** Тяжёлый отчёт одной организации потребляет ресурсы общей БД. В Release 1.0 митигируется только rate limiting и пагинацией.
8. **Миграция существующей prototype-БД нетривиальна.** Требуется пятиэтапная процедура с backfill, валидацией консистентности и переносом объектов хранилища (ТЗ 40).
9. **Frontend получил новое сквозное состояние.** `BranchContext` затрагивает кэш, отмену запросов, навигацию и доступность действий — источник потенциальных дефектов UX, покрываемый тестами `TEST-TEN-035`, `TEST-TEN-036`.

## 4. Rejected alternatives

### 4.1. Отдельная база данных на филиал

**Отклонено.** Дало бы сильнейшую изоляцию, но: создание филиала превращается в инфраструктурную операцию (провижининг БД, миграции, мониторинг, бэкап) вместо продуктовой; миграции применяются к N базам с риском рассогласования версий схемы; сводная аналитика организации требует межбазовых запросов или отдельного хранилища; стоимость эксплуатации растёт линейно с числом филиалов. Требование ТЗ — одна PostgreSQL.

### 4.2. Отдельная база данных на организацию

**Отклонено для Release 1.0** по тем же причинам. Отмечается как более защитимая эволюция, чем разделение по филиалам: граница совпадает с границей арендатора, а сводная аналитика внутри организации остаётся однобазовой. Может быть пересмотрено при появлении арендаторов с регуляторным требованием физического разделения. Выбранная схема этому не препятствует: `OrganizationId` уже присутствует во всех данных и является естественным ключом шардирования.

### 4.3. Отдельный backend на филиал

**Отклонено.** Микросервисная или мульти-инстансная топология противоречит зафиксированной архитектуре модульного монолита (ТЗ раздел 5), требует service discovery, распределённых транзакций для операций уровня организации и оркестрации деплоя. Не даёт ни одного преимущества по изоляции, которого не даёт scope-проверка в одном процессе: границей всё равно остаётся код авторизации.

### 4.4. Отдельное React-приложение на филиал

**Отклонено.** Состав экранов филиалов идентичен; различаются только данные. N сборок означают N путей регрессии, N обновлений при каждом изменении и невозможность построить экран сравнения филиалов. Маршрутизация по филиалу (`/branch-1/*`) отклонена по той же причине: филиал является контекстом данных, а не разделом приложения.

### 4.5. Branch как ещё одна Category (или как префикс имени категории)

**Отклонено.** Наиболее опасная из рассмотренных альтернатив, поскольку выглядит самой дешёвой. Категория «C# — Худжанд» не решает ни одной задачи: не появляется администратор филиала; аналитика по филиалу требует парсинга имени; уникальность имени остаётся глобальной; Lead одного филиала остаётся технически способным быть назначенным в категорию другого; ни одно ограничение БД не начинает различать филиалы. Изоляция подменяется соглашением об именовании, которое нарушается первой же опечаткой.

### 4.6. Только UI-фильтрация

**Отклонено.** Скрытие данных чужого филиала на клиенте не является защитой: API остаётся доступным напрямую, а frontend явно объявлен не границей безопасности (`FE-012`). Этот вариант эквивалентен отсутствию изоляции при наличии её видимости — худшее из возможных состояний, поскольку создаёт ложную уверенность.

### 4.7. Добавление BranchId только в User

**Отклонено.** Минимально инвазивный вариант, дающий иллюзию решения. Позволил бы отфильтровать списки пользователей, но: `Assignment`, `Submission`, `Review`, `TaskEvent` не имели бы филиала и не могли бы быть отфильтрованы иначе как join'ом через текущего владельца; при переводе пользователя между филиалами **вся его история мгновенно сменила бы филиал**, исказив аналитику обоих; ни один composite FK не может быть построен; фоновые задачи, работающие без пользовательского контекста, не имели бы источника scope. Immutable snapshot scope в данных — обязательное условие корректности, а не оптимизация.

### 4.8. Доверие к BranchId из запроса

**Отклонено.** Приём `branchId` из тела запроса или из недоверенного заголовка любым пользователем превращает изоляцию в декларацию: клиент сам заявляет, чьи данные он хочет видеть. Принятое решение: scope всегда вычисляется сервером из claims; единственное исключение — `X-MTF-Branch-Id` для Organization Admin, который **сужает** видимость в пределах уже подтверждённой Organization и валидируется на каждом запросе (`TEN-032a`, `TEN-036a`).

### 4.9. Создание множества новых ролей

**Отклонено.** `SuperAdmin`, `HeadOfficeAdmin`, `BranchAdminRole`, `OrganizationAdminRole` не добавили бы ни одного нового разрешения: все они выражаются парой «роль Admin + контур». Каждая новая роль потребовала бы строки в матрице прав Приложения A, ветки в каждой authorization policy, отдельного набора тестов и отдельного пути в UI. Ортогональное измерение `AdminScope` даёт тот же результат одним полем и одним CHECK-ограничением.

### 4.10. Отдельный бакет MinIO на филиал

**Отклонено.** Потребовало бы динамического управления политиками bucket при каждом создании филиала, превращая продуктовую операцию в инфраструктурную, и усложнило бы backup и репликацию. Принято: один бакет, scope в префиксе ключа, авторизация при выдаче presigned URL (`TEN-066`).

### 4.11. PostgreSQL RLS как основной механизм изоляции

**Отклонено для Release 1.0** — обоснование в разделе 2.6. Не отвергнуто принципиально: остаётся кандидатом на hardening.

## 5. Migration notes

Определены **два режима** (ТЗ раздел 40).

**Режим A — новая БД.** Initial migration создаёт схему 2.2 целиком: scope-колонки сразу `NOT NULL`, composite FK создаются вместе с таблицами. Временно nullable арендные колонки не создаются (`TEN-081`).

**Режим B — существующая prototype-БД.** Пять этапов:

| Этап | Содержание | Обратимость |
|---|---|---|
| 1 | Создать Organization и HeadOffice Branch; добавить scope-колонки как nullable; backfill всех существующих данных | Полная (`DROP COLUMN`) |
| 2 | Pre-migration validation query: orphan-строки, рассогласование scope между связанными сущностями, нарушения `USER-023`, дубли имён категорий в филиале, множественные HeadOffice. Ручное устранение нарушений; создание composite unique index | Изменений схемы нет |
| 3 | Composite FK → `NOT NULL` → CHECK → индексы. **Порядок обязателен** | Полная (`DROP CONSTRAINT`) |
| 4 | `Admin` → Organization Admin; `Lead`/`Mentor`/`Category` → HeadOffice Branch; перенос объектов MinIO на новый шаблон ключа **копированием** | Частичная (из бэкапа) |
| 5 | Smoke-тесты, 40 isolation-тестов, проверка арендной целостности. Только после этого — удаление transitional-кода | Точка невозврата |

Ключевые правила:

- **Автоматическое «исправление» данных запрещено** (`TEN-084`): неверно угаданная принадлежность строки к филиалу создала бы утечку, неотличимую от корректных данных. Все исправления выполняются вручную с протоколированием.
- **Backup обязателен** перед этапом 1 (PostgreSQL + снимок бакета); шаг прерывается, если бэкап не подтверждён (`TEN-089`).
- DDL в PostgreSQL транзакционен: этапы 1, 3 и 4 выполняются каждый в собственной транзакции целиком. Исключение — `CREATE INDEX CONCURRENTLY` (`TEN-088`).
- Соблюдается правило expand → migrate → contract (`DEPLOY-019`): удаление transitional-кода выполняется отдельным релизом.

**Bootstrap** создаёт в одной транзакции: Organization → HeadOffice Branch → Organization Admin → `SetPassword`-токен → Outbox → AuditLog (`DEPLOY-030`). Первый администратор создаётся именно как **Organization Admin**, а не как администратор главного офиса: администратор, привязанный к филиалу, не смог бы создать второй филиал (`DEPLOY-031`). Bootstrap идемпотентен; уникальные индексы — финальная защита при гонке двух контейнеров (`DEPLOY-032`). Default password отсутствует полностью.

**Порядок внедрения.** Фаза 0.5 «Tenancy foundation» обязана быть завершена до начала фазы 1 (`TEN-019`). Добавление арендной границы после реализации бизнес-логики потребовало бы пересмотра каждого handler и каждого запроса; введение её до бизнес-логики делает scope естественной частью каждого нового запроса. Это прямой вывод из раздела 1.3: смешение данных возникает именно тогда, когда scope добавляется постфактум и неизбежно пропускается в части запросов.

## 6. Security notes

1. **Изоляция филиалов — граница безопасности, а не UI-фильтр.** Ни один тест раздела 31.9 не может быть помечен как «известное ограничение» (`TEST-014`).
2. **Единый 404.** Чужая Organization, чужой Branch, чужая Category, чужой объект Mentor и несуществующий объект неотличимы по ответу. Коды `FOREIGN_BRANCH`, `FOREIGN_ORGANIZATION`, `BRANCH_NOT_FOUND`, `ORGANIZATION_NOT_FOUND` отсутствуют в каталоге намеренно и не могут быть добавлены (`TEN-006`).
3. **`totalCount`, поиск, фильтры и экспорт** не раскрывают существование данных вне scope (`TEN-002`).
4. **Заголовок scope не является утверждением о правах.** Он принимается только от Organization Admin, только после проверки принадлежности Organization, только в разрешённых операциях и валидируется на каждом запросе — филиал мог быть деактивирован между запросами (`TEN-035a`).
5. **Мутация в режиме «Все филиалы» запрещена всегда.** Такая операция не имеет однозначного отката и не может быть корректно отражена одной записью AuditLog (`TEN-034`).
6. **Ownership не пробивает границу Branch.** После перевода пользователь теряет доступ к рабочим данным прежнего филиала, включая собственные задачи (`USER-017`). Отличие от уровня Category осознанное: перевод между категориями остаётся внутри одного арендного контура, перевод между филиалами — нет.
7. **Любое изменение scope обесценивает выданные токены**: `TokenVersion++`, отзыв всех RefreshToken, инвалидация активных security-токенов, повторный вход (`AUTH-034`). Гарантия окна остаётся честной: не позднее 30 секунд для access token, немедленно для refresh.
8. **Email остаётся глобально уникальным.** Уникальность в пределах Organization потребовала бы выбора арендатора на форме входа либо неоднозначного разрешения учётной записи (`TEN-028`). Следствие: адрес электронной почты не может быть переиспользован в двух организациях — принято осознанно.
9. **Ключи дедупликации и кэширования включают scope.** Без этого одноимённые события разных филиалов конфликтовали бы по уникальному индексу и **молча подавляли** бы друг друга (`TEN-043`), а AI-резюме одного филиала возвращалось бы из кэша для другого (`TEN-076`). Оба дефекта относятся к классу «тихая утечка» — наиболее опасному, поскольку не проявляется как ошибка.
10. **Рассогласование scope в хранилище не приводит к удалению объекта.** Вместо удаления создаётся security alert: рассогласование является признаком дефекта или вмешательства, и уничтожение улики недопустимо (`TEN-068`).
11. **Метрики не используют высококардинальные labels** (`userId`, `assignmentId`, email): помимо деградации системы сбора это создало бы канал раскрытия персональных данных через `/metrics` (`OBS-010`).
12. **Рост `cross_scope_reference_rejected_total` классифицирован как Critical.** В корректно работающей системе счётчик обязан оставаться нулевым; любое увеличение означает дефект или попытку обхода изоляции.
13. **Изоляция проверяется на уровне БД, а не только через API.** Тест `TEST-TEN-040` выполняет прямые `INSERT`/`UPDATE` под ролью приложения для всех 21 composite FK: его цель — доказать, что изоляция не зависит от корректности кода приложения.
