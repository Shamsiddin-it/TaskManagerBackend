## 1. Executive summary

Версия 2.1 является технически корректным и внутренне согласованным документом: после предыдущего аудита в ней устранены все дефекты реализуемости, конечный автомат непротиворечив, API-контракт полон, трассируемость сплошная. Настоящий аудит **не выявил регрессий** в этих областях и не изменил ни одно из принятых там решений.

Предметом настоящего аудита является другой вопрос: **выдержит ли модель добавление второго филиала.**

Ответ — **нет**. Версия 2.1 спроектирована для одной организации с одним набором учебных направлений. Верхней бизнес-границей является `Category`; сущностей `Organization`, `Branch`, полей `OrganizationId`, `BranchId` и понятия административного контура в модели не существует. Единственная роль `Admin` по построению видит все категории и все административные данные системы.

Ключевой вывод аудита формулируется так:

> **Дефекты смешения данных при добавлении второго филиала возникают не из-за ошибок реализации, а из-за отсутствия носителя арендного контекста в модели данных.** Ни один из них не может быть устранён проверкой в коде приложения, потому что проверять нечего: филиал не является атрибутом ни одной строки. Это делает все такие дефекты **неустранимыми на уровне реализации** и относит их к классу Critical.

## 2. Почему изоляции по Category оказалось недостаточно

### 2.1. Природа дефекта

`Category` — **предметная** граница (учебное направление), а не **арендная** (организационная принадлежность данных). Версия 2.1 использует её как верхнюю границу изоляции, что корректно ровно до тех пор, пока в системе существует один набор направлений.

При появлении второго филиала возникают две категории с одинаковым смыслом («C#») и разным составом участников. Модель 2.1 не может их различить: у неё нет ни поля, ни ограничения, ни claim, ни индекса, выражающего принадлежность к филиалу.

### 2.2. Конкретные механизмы смешения

Ниже — исчерпывающий перечень областей, в которых данные двух филиалов смешались бы, с указанием точного механизма. Каждая строка проверена по тексту версии 2.1.

| # | Область | Механизм смешения в версии 2.1 | Severity |
|---|---|---|---|
| 1 | Пользователи | `GET /users` для Admin возвращает всех пользователей системы (`USER-010`); фильтра по филиалу не существует | Critical |
| 2 | Категории | `ux_categories_name_lower` — **глобальная** уникальность имени. Второй филиал физически не смог бы создать собственную категорию «C#» | Critical |
| 3 | Расписание | `Topic`/`TopicAssignment` наследуют scope только от `Category`; при слиянии категорий Lead одного филиала ведёт расписание другого | Critical |
| 4 | Задания | `Assignment.AssignedToId` — «Mentor той же CategoryId»; филиал не проверяется ни FK, ни валидацией | Critical |
| 5 | Сдачи | `Submission` не имеет собственного scope; наследуется от Assignment, который сам не различает филиалы | Critical |
| 6 | Проверки | `Review.ReviewerId` — «Lead той же CategoryId»; Lead чужого филиала мог бы вынести решение | Critical |
| 7 | Уведомления | `DeduplicationKey = {eventType}:{entityId}:{channel}:{discriminator}` — без филиала. Одноимённые события двух филиалов конфликтуют по `ux_notification_outbox_dedup`, и уведомление одного **молча подавляет** уведомление другого | Critical |
| 8 | AuditLog | Единственная роль Admin читает журнал всей системы (`AUD-002`); арендных полей нет | Critical |
| 9 | Аналитика | Группировка по `Category` объединила бы показатели несвязанных учебных потоков; правило ≥5 менторов обходилось бы объединением филиалов | Critical |
| 10 | AI-резюме | `CacheKey = SHA256(scope + subjectUserId + categoryId + …)` — без филиала. Отчёт одного филиала **возвращается из кэша** для другого | Critical |
| 11 | Файлы | `StorageKey = submissions/{categoryId}/{assignmentId}/…` — при одноимённых категориях префиксы операционно неразличимы | Critical |
| 12 | Фоновые задачи | Планировщик выбирает «активные Category», BDA — «активных Mentor категории»; ни один запрос не ограничен филиалом | Critical |
| 13 | Административные операции | Единственный контур Admin: деактивация, смена ролей, force-cancel применимы к данным любого филиала | Critical |

### 2.3. Почему это не UI-проблема

Три соображения, зафиксированные в ТЗ 2.2 и ADR-001:

1. **API доступен напрямую.** Скрытие данных чужого филиала на клиенте не влияет на ответ сервера. Frontend явно объявлен не границей безопасности (`FE-012`) начиная с версии 2.1.
2. **Фоновые задачи не имеют пользовательского контекста.** Планировщик, джоб просрочки и Outbox worker выполняются без принципала; UI-фильтр к ним неприменим в принципе.
3. **Ограничения БД не различают филиалы.** Даже при идеальной реализации приложения ошибочная строка вставляется без препятствий: `fk_assignments_assigned_to` версии 2.1 проверяет существование пользователя, но не его филиал.

### 2.4. Почему добавление `BranchId` только в `User` не решило бы задачу

Этот вариант рассматривался и отклонён (ADR-001 §4.7) как **опаснейший из «дешёвых»**:

- `Assignment`, `Submission`, `Review`, `TaskEvent` не получили бы филиала и фильтровались бы join'ом через текущего владельца;
- при переводе пользователя между филиалами **вся его история мгновенно сменила бы филиал**, исказив аналитику обоих задним числом;
- ни один composite FK не мог бы быть построен: FK связывает колонки таблиц, а не результаты join;
- фоновые задачи не имели бы источника scope.

Immutable snapshot scope в самих данных (`TEN-018`) является **обязательным условием корректности**, а не оптимизацией.

## 3. Принятая архитектура Organization / Branch

Полное обоснование — [`ADR-001-organization-branch-isolation.md`](./ADR-001-organization-branch-isolation.md). Краткая сводка принятых решений:

| Решение | Формулировка | Раздел ТЗ |
|---|---|---|
| Иерархия | `Organization → Branch → Category → (всё остальное)` | 38.1 |
| Главный офис | Обычный `Branch` с `IsHeadOffice=true`; ровно один на Organization; специального контура не образует | 10.18, 38.1 |
| Модель арендности | Shared database / shared schema; одна PostgreSQL, одна схема, глобально уникальные UUID | 38.2 |
| Носитель scope | Прямые `OrganizationId`/`BranchId` в 14 сущностях; денормализация вниз по иерархии | 10.20, Приложение M |
| Иммутабельность | `OrganizationId`/`BranchId` — immutable snapshot scope; история не переносится | 10.6.4, `TEN-018` |
| Ограничения БД | 13 composite unique index + **21 composite FK** + 11 новых CHECK | 12.1a, 12.2, 12.2a |
| RLS | **Не используется** в Release 1.0; остаётся кандидатом на hardening | 12.8, `TEN-030` |
| Роли | Ровно три; новые не вводятся. Административный контур — `AdminScope ∈ {Organization, Branch}` | 8, `TEN-011` |
| Изоляция | Шесть уровней, порядок обязателен | 9.1 |
| Scope-контекст | `ICurrentUserContext` + `IBranchContext`; заголовок `X-MTF-Branch-Id` только для Organization Admin | 38.3 |
| Мутации | В режиме «Все филиалы» запрещены всегда | `TEN-034` |
| Frontend | Одно SPA, маршруты `/admin/*`, `/lead/*`, `/mentor/*` сохранены; `BranchContext` — не граница безопасности | 24.7, 24.8 |

Сохранено без изменений: один модульный монолит, один ASP.NET Core API, одна PostgreSQL, одна схема, один MinIO, один React SPA, общая инфраструктура.

Не тронуто по требованию задания и подтверждено проверкой: статусы Assignment, правила Submission, Review lifecycle, `AllowLateSubmission`, правила дедлайнов, Outbox retry, refresh rotation, `refreshCoordinator`, `authEvents`, password onboarding, отсутствие публичной регистрации, маршруты `/admin/*`, `/lead/*`, `/mentor/*`.

## 4. Найденные проблемы

Для каждой проблемы указаны: severity, старое состояние (версия 2.1), риск, внесённое исправление, раздел ТЗ 2.2, статус.

### 4.1. Critical (12)

Критическими считаются дефекты, приводящие к смешению данных филиалов, неустранимые на уровне реализации либо создающие «тихую» утечку, не проявляющуюся как ошибка.

---

**C-01. Отсутствует Organization — нет верхней арендной границы**

- **Старое состояние:** сущности `Organization` не существует; ни одна таблица не содержит `OrganizationId`; понятие арендатора в документе отсутствует.
- **Риск:** система принципиально не может обслуживать более одной организации. Любая попытка добавить вторую приводит к полному смешению всех данных без единого механизма противодействия.
- **Исправление:** введена сущность `Organization` (Id, Name, NormalizedName, Slug, IsActive, CreatedAt, UpdatedAt, ConcurrencyToken); `OrganizationId` добавлен во все tenant-scoped сущности и **всем** пользователям без исключения; значение никогда не принимается от пользователя (`ORG-021`); создание — только provisioning-процессом (`ORG-001`, `ORG-002`); физическое удаление запрещено (`ORG-006`).
- **Раздел ТЗ:** 10.17, 38.1, 38.2, Приложение M
- **Статус:** **Fixed**

---

**C-02. Отсутствует Branch — нет операционной границы изоляции**

- **Старое состояние:** сущности `Branch` не существует; филиал не выражен ничем.
- **Риск:** второй филиал не может быть представлен в модели иначе как второй категорией с изменённым именем — подмена границы безопасности соглашением об именовании (ADR-001 §4.5).
- **Исправление:** введена сущность `Branch` (Id, OrganizationId, Name, NormalizedName, Code, Address, TimeZoneId, IsHeadOffice, IsActive, CreatedAt, UpdatedAt, ConcurrencyToken); `BranchId` добавлен во все branch-scoped сущности; определён полный жизненный цикл филиала.
- **Раздел ТЗ:** 10.18, 39
- **Статус:** **Fixed**

---

**C-03. Единственная роль Admin видит все данные системы**

- **Старое состояние:** `Role='Admin'` без каких-либо ограничений области; `GET /users` — «Admin (все)», `GET /categories` — «Admin (все)», AuditLog — «только Admin», без контура.
- **Риск:** администратор филиала Худжанд, будучи технически обычным Admin, получал бы полный доступ к пользователям, категориям, заданиям, файлам, аудиту и аналитике главного офиса. Отдельного администратора филиала создать невозможно.
- **Исправление:** введён `AdminScope ∈ {Organization, Branch}` как ортогональное измерение при сохранении ровно трёх Role (`TEN-011`, `TEN-012`); определены четыре допустимых сочетания scope-полей `User` (`USER-023`); полномочия обоих администраторов расписаны в 8.1 и 8.2; Приложение A переписано с четырьмя колонками; формулировка «Admin — любая» запрещена (`TEN-035`).
- **Раздел ТЗ:** 8.1, 8.2, 8.5, 8.6, Приложение A, Приложение N
- **Статус:** **Fixed**

---

**C-04. Глобальная уникальность имени Category блокирует второй филиал**

- **Старое состояние:** `ux_categories_name_lower — UNIQUE (LOWER(name))`.
- **Риск:** филиал Худжанд физически не может создать категорию «C#», поскольку она уже существует в главном офисе. Обход возможен только переименованием («C# Худжанд»), то есть подменой структуры данных именованием.
- **Исправление:** уникальность заменена на `ux_categories_branch_normalized_name — UNIQUE (branch_id, normalized_name)` (`CAT-021`); `NormalizedName` вычисляется сервером; одноимённые категории в разных филиалах объявлены разными сущностями без общих данных (`TEN-002a`); покрыто тестами `TEST-TEN-030`, `TEST-TEN-031`, `TEST-DB-012`.
- **Раздел ТЗ:** 10.2, 12.1, 12.1a, 39.4
- **Статус:** **Fixed**

---

**C-05. Внешние ключи не различают филиалы**

- **Старое состояние:** `Assignment.AssignedToId` — FK на `users` с текстовым требованием «той же CategoryId»; `Review.ReviewerId` — «Lead той же CategoryId». Требование выражено **только текстом**; на уровне БД проверяется лишь существование пользователя.
- **Риск:** Assignment может быть назначен Mentor другого филиала, Review — вынесен Lead другого филиала. При корректной реализации приложения дефект не проявляется; при любой ошибке handler'а или прямом доступе к БД — проявляется как утечка, не отклоняемая ничем.
- **Исправление:** введены **21 composite FK**, делающие cross-scope связь физически невозможной, в том числе `fk_assignments_assignee_scope`, `fk_assignments_assigner_scope`, `fk_reviews_reviewer_scope`, `fk_submissions_assignment_scope`, `fk_task_events_assignment_scope`, `fk_topic_assignments_topic_scope`, `fk_users_category_scope`. Добавлены 13 composite unique index как цели этих FK. Нарушение → 409 `CROSS_SCOPE_REFERENCE`. Проверяется тестом `TEST-TEN-040`, выполняющим прямые `INSERT`/`UPDATE` в обход приложения.
- **Раздел ТЗ:** 12.1a, 12.2a, 9.7, Приложение M
- **Статус:** **Fixed**

---

**C-06. DeduplicationKey уведомлений не содержит арендного scope — тихое подавление**

- **Старое состояние:** `DeduplicationKey = {eventType}:{entityId}:{channel}:{discriminator}`; уникальный индекс `ux_notification_outbox_dedup`; вставка через `ON CONFLICT DO NOTHING`.
- **Риск:** событие `category-no-lead:{categoryId}:{localDate}` для категории «C#» главного офиса и одноимённое событие филиала Худжанд при совпадении дискриминаторов конфликтуют по уникальному индексу. Вторая вставка **молча игнорируется** — уведомление одного филиала подавляет уведомление другого. Дефект относится к классу «тихая утечка»: он не проявляется как ошибка, не попадает в логи и обнаруживается только по факту неполученного уведомления.
- **Исправление:** ключ расширен обязательным префиксом `{organizationId}:{branchId|"org"}:` (`NTF-015`, `TEN-043`); в `NotificationOutbox` добавлены `OrganizationId` (NOT NULL), `BranchId`, `CategoryId` с immutable scope; покрыто тестом `TEST-TEN-019`.
- **Раздел ТЗ:** 10.15, 18.5, 18.8
- **Статус:** **Fixed**

---

**C-07. AiSummary.CacheKey не содержит арендного scope — выдача чужого отчёта**

- **Старое состояние:** `CacheKey = SHA256(scope + subjectUserId + categoryId + periodStart + periodEnd + metricsHash + promptVersion + modelId)`; `ux_ai_summaries_cache_key — UNIQUE (cache_key)`; повторный запрос с тем же ключом возвращает сохранённый отчёт **без обращения к провайдеру**.
- **Риск:** при одноимённых категориях с совпадающими `metricsHash` (что реально при близких показателях) отчёт филиала A возвращается пользователю филиала B из кэша. Прямая утечка агрегированных данных чужого филиала, также относящаяся к классу «тихая».
- **Исправление:** ключ расширен `organizationId`, `branchId` (либо маркером `ALL_BRANCHES`), `reportType` и `metricsVersion` (`AI-009`, `TEN-076`); в `AiSummary` добавлены `OrganizationId` (NOT NULL) и `BranchId`; `Scope` расширен значениями `Branch` и `Organization` с CHECK-инвариантом формы; Branch Admin не может запросить резюме другого филиала (`TEN-077`); покрыто тестом `TEST-TEN-030`.
- **Раздел ТЗ:** 10.16, 22.5, 22.8
- **Статус:** **Fixed**

---

**C-08. StorageKey не содержит арендного scope**

- **Старое состояние:** `submissions/{categoryId}/{assignmentId}/{submissionId}{extension}`.
- **Риск:** объекты двух филиалов неразличимы по префиксу; branch-scoped экспорт невозможен без обращения к БД по каждому объекту; операционный разбор инцидента (какие файлы затронуты) требует полного обхода; orphan cleanup не может обрабатывать филиалы раздельно.
- **Исправление:** ключ изменён на `submissions/{organizationId}/{branchId}/{categoryId}/{assignmentId}/{submissionId}{extension}` (`SUB-009`); значения берутся исключительно из Assignment на сервере, приём из `multipart/form-data` запрещён (`TEN-061`); явно указано, что scope в пути **не является механизмом авторизации** (`TEN-062`); `Submission.StorageKey` расширен до `varchar(320)`; определён перенос существующих объектов при миграции (`TEN-063`).
- **Раздел ТЗ:** 10.7, 17.1, 17.8, 40.2
- **Статус:** **Fixed**

---

**C-09. Планировщик и BDA не ограничены филиалом**

- **Старое состояние:** `SCH-002` — «для каждой активной Category»; `SCH-013` — «среди активных Mentor категории (`IsActive=true`, `Role='Mentor'`)».
- **Риск:** при одноимённых категориях планировщик создаёт задание в категории одного филиала и назначает его ментору другого. Дефект возникает **без участия пользователя**, в фоновом режиме, и обнаруживается ментором как задание из чужого учебного потока.
- **Исправление:** цепочка выборки расширена до `Organization → Branch → Category → Topic → TopicAssignment → Mentor`, обрывается на первом неактивном звене (`SCH-002`, `TEN-050`); BDA считает загрузку строго внутри `(organization_id, branch_id, category_id)` (`TEN-051`); `AutoGenerationKey` включает scope, индекс заменён на `ux_assignments_auto_generation_key_scoped` (`SCH-009`, `SCH-023`); определён арендный scope **каждой** фоновой задачи (`TEN-052`); покрыто тестами `TEST-TEN-020`, `TEST-TEN-021`, `TEST-TEN-022`.
- **Раздел ТЗ:** 20.2, 20.3, 20.4, 20.8
- **Статус:** **Fixed**

**C-10. AuditLog и NotificationOutbox не имеют арендного scope**

- **Старое состояние:** обе сущности содержат только `ActorId`/`UserId`; читаются единственной ролью Admin без ограничений.
- **Риск:** администратор филиала видит административные действия и уведомления всех филиалов, включая события безопасности уровня организации. Ограничить выборку нечем: арендных колонок нет.
- **Исправление:** в `AuditLog` добавлены `OrganizationId` (NOT NULL), `BranchId`/`CategoryId` (nullable по строгому списку), `ActorRole`, `ActorAdminScope`; в `NotificationOutbox` — `OrganizationId` (NOT NULL), `BranchId`/`CategoryId` с immutable scope; определены область видимости для обоих администраторов (`TEN-040`, `TEN-046`), закрытый перечень Organization-level действий (`TEN-048`), правила адресации получателей (`TEN-044`), запрет доставки уведомлений Branch Admin чужого филиала (`TEN-045`); добавлены CHECK `ck_audit_logs_branch_scope` и `ck_notification_outbox_branch_scope`; покрыто тестами `TEST-TEN-018`, `TEST-TEN-019`.
- **Раздел ТЗ:** 10.14, 10.15, 18.8, 27.6
- **Статус:** **Fixed**

**C-11. JWT claims не содержат арендного контекста**

- **Старое состояние:** `AUTH-003` — claims `sub`, `role`, `category_id` (отсутствует у Admin), `tv`, `jti`, `iat`, `exp`, `iss`, `aud`.
- **Риск:** сервер не имеет источника арендного контекста запроса. Даже при добавлении колонок в БД каждый handler был бы вынужден выполнять дополнительный запрос за филиалом пользователя, а middleware не мог бы отклонить запрос до бизнес-логики. Ложная гарантия «изоляции по claim» при отсутствии claim.
- **Исправление:** добавлены claims `admin_scope`, `org_id`, `branch_id`; `org_id` присутствует **всегда** (`AUTH-033`); зафиксирована таблица присутствия claims по типам пользователей (`AUTH-031`); middleware отклоняет токен с набором claims, не соответствующим ни одной допустимой строке, → 401 до любой бизнес-логики (`AUTH-032`); frontend объявлен недоверенным источником профиля (`AUTH-036`).
- **Раздел ТЗ:** 16.1, 16.1.1, 16.9
- **Статус:** **Fixed**

**C-12. Изменение филиала не инвалидирует выданные токены**

- **Старое состояние:** `AUTH-027` — `TokenVersion` увеличивается при смене пароля, роли, категории, деактивации, reuse detection. Филиала и административного контура в перечне нет (и быть не могло — сущностей не существовало).
- **Риск:** после перевода пользователя между филиалами его действующий access token продолжает содержать прежний `branch_id` и принимается сервером до истечения TTL. Пользователь сохраняет полный доступ к данным прежнего филиала на срок до 15 минут — прямая утечка после административного действия, призванного этот доступ прекратить.
- **Исправление:** перечень триггеров расширен изменением `BranchId`, `AdminScope` и приведён в виде таблицы с указанием отзыва RefreshToken, инвалидации security-токенов и требования повторного входа (`AUTH-034`); правило сформулировано одним предложением: любое изменение scope или уровня доступа немедленно обесценивает выданные токены; в `ReasonRevoked` добавлены `BranchChanged` и `AdminScopeChanged`; покрыто тестами `TEST-TEN-026`, `TEST-TEN-027`, `TEST-TEN-028`.
- **Раздел ТЗ:** 10.10, 16.2, 16.7, 39.6
- **Статус:** **Fixed**

## 6. Новые сущности

| Сущность | Назначение | Ключевые инварианты |
|---|---|---|
| `Organization` | Верхняя арендная граница | `Slug` и `NormalizedName` глобально уникальны и формируются сервером; создаётся только provisioning; физическое удаление запрещено; пользователь одной Organization не видит существования другой |
| `Branch` | Операционная граница изоляции | Принадлежит ровно одной Organization (immutable); `Code` и `NormalizedName` уникальны в пределах Organization; **ровно один** `IsHeadOffice=true` на Organization; физическое удаление запрещено; `TimeZoneId` валидируется по IANA |

Решение по `OrganizationSettings`: **не вводится** в Release 1.0 (`ORG-024`). Все существующие настройки относятся к уровню Category, часовой пояс дополнительно — к уровню Branch. Настроек уровня всей организации в текущем scope не существует.

## 7. Роли и AdminScope

Сохранены ровно три `Role`. Новые роли не введены.

| Тип | Role | AdminScope | OrganizationId | BranchId | CategoryId |
|---|---|---|---|---|---|

| Lead | `Lead` | **NULL** | NOT NULL | NOT NULL | NOT NULL |

Допустимы ровно эти четыре сочетания; иные запрещены `ck_users_scope_shape`, `ck_users_role_admin_scope`, `ck_users_role_category` (тест `TEST-DB-010`).

Принятые окончательные решения по спорным вопросам:

| Вопрос | Решение | Обоснование |
|---|---|---|
| Может ли Branch Admin создать Branch Admin? | **Нет.** Только Organization Admin | Самовоспроизводство контура филиала лишает организацию контроля над составом администраторов и даёт путь эскалации, ненаблюдаемый на уровне организации |
| Может ли Branch Admin редактировать свой Branch? | **Нет.** Только `GET` | `TimeZoneId` влияет на умолчания новых категорий, `Code` — на отчёты уровня организации; разделение полей породило бы два набора правил ради второстепенной возможности |
| Видит ли Branch Admin список филиалов? | **Нет.** Только свой филиал в profile/context | Перечень филиалов раскрывает состав организации |
| Сколько администраторов допустимо? | Несколько Organization Admin и несколько Branch Admin | Единственный администратор — единая точка отказа при потере доступа |
| Ограничение «один активный Lead» | Сохранено в пределах Category | Category принадлежит одному Branch, поэтому ограничение автоматически branch-scoped |

## 12. Migration impact

Два режима (раздел 40 ТЗ).

**Режим A — новая БД:** initial migration создаёт схему 2.2 целиком; временно nullable арендные колонки не создаются.

**Режим B — существующая prototype-БД:** 5 этапов.

| Этап | Содержание | Обратимость |
|---|---|---|
| 1 | Organization + HeadOffice; scope-колонки как nullable; backfill | Полная |
| 2 | Pre-migration validation query (5 групп проверок); ручное устранение нарушений; composite unique index | Схема не изменяется |
| 3 | Composite FK → `NOT NULL` → CHECK → индексы (порядок обязателен) | Полная |
| 4 | `Admin` → Organization Admin; `Lead`/`Mentor`/`Category` → HeadOffice; перенос объектов MinIO **копированием** | Частичная (из бэкапа) |
| 5 | Smoke-тесты + 40 isolation-тестов + проверка арендной целостности; затем удаление transitional-кода | Точка невозврата |

Ключевые правила: автоматическое «исправление» данных запрещено (`TEN-084`); backup обязателен и подтверждается до начала (`TEN-089`); DDL транзакционен, исключение — `CREATE INDEX CONCURRENTLY` (`TEN-088`); соблюдается expand → migrate → contract.

Фаза 0.5 «Tenancy foundation» обязана быть завершена до фазы 1 (`TEN-019`): добавление арендной границы после реализации бизнес-логики потребовало бы пересмотра каждого handler и неизбежно пропустило бы часть запросов — тот самый механизм, который порождает дефекты раздела 2 настоящего отчёта.

## 14. Race conditions

Приложение K расширено с 16 до **25 сценариев**. Добавлено 9:

| # | Сценарий | Защита | Ожидаемый результат |
|---|---|---|---|
| 17 | Два Organization Admin создают Branch с одним `Code` | `ux_branches_organization_code` | 201 / 409 `BRANCH_ALREADY_EXISTS`; частичного состояния нет |
| 18 | Два запроса назначают главный офис разным филиалам | `ux_branches_single_head_office` + `FOR UPDATE` по `organizations` | 200 / 409 `CONCURRENCY_CONFLICT`; ровно один HeadOffice в любой момент |
| 19 | Деактивация Branch ‖ создание Assignment | `FOR SHARE`/`FOR UPDATE` по `branches` | Одна операция; при победе деактивации — 403 `BRANCH_INACTIVE` |
| 20 | `change-branch` ‖ создание Assignment для того же Mentor | `FOR UPDATE` по `users` + проверка нетерминальных задач | 409 `BRANCH_CHANGE_BLOCKED` либо перевод; промежуточного состояния нет |
| 21 | `change-branch` ‖ `login`/`refresh` | `TokenVersion++` + отзыв refresh-токенов в транзакции | `refresh` → 401; `login` выдаёт токены **нового** scope |
| 22 | Category с одним `Name` в одном Branch | `ux_categories_branch_normalized_name` | 201 / 409 `RESOURCE_ALREADY_EXISTS` |
| 23 | Category с одним `Name` в разных Branch | Конфликта нет по построению индекса | **Обе успешны**: две независимые сущности |
| 24 | Деактивация Branch ‖ прогон планировщика | Чтение `is_active` в транзакции вставки + `ON CONFLICT DO NOTHING` | Полная генерация либо ни одной; частичного набора нет |
| 25 | Смена `AdminScope` ‖ административная мутация | `TokenVersion++` + проверка `tv` в middleware | Старые права до коммита либо 401 `TOKEN_VERSION_MISMATCH`; частичных прав нет |

Для каждого указаны ограничение БД, уровень изоляции, блокировка строки, необходимость concurrency token, ожидаемый HTTP-результат и отсутствие частичного изменения. Ни один сценарий не защищён только предварительной проверкой в application service.

## 15. Остаточные риски

Риски версии 2.1 (`R-01`…`R-11` предыдущего отчёта) сохраняются в полном объёме и не пересматривались. Ниже — риски, введённые или обострённые арендной моделью.

| # | Риск | Уровень | Проявление | Митигация |
|---|---|---|---|---|
| RA-01 | Общая инфраструктура — общий blast radius | **Средний** | Отказ PostgreSQL или MinIO затрагивает все филиалы всех организаций одновременно | Соответствует SLO 99.5% и RTO 4 ч. Арендно-независимая доступность потребовала бы разделения БД (ADR-001 §4.1) — вне Release 1.0 |
| RA-02 | «Шумные соседи» | **Средний** | Тяжёлый отчёт одной организации потребляет ресурсы общей БД, замедляя другие | Rate limiting (`SEC-007`), обязательная пагинация, tenant-ведущие индексы (`TEN-029`). Изоляции ресурсов на уровне арендатора нет |
| RA-03 | Self-service восстановление филиала отсутствует | **Средний** | Ошибочное массовое действие в одном филиале не откатывается без полного восстановления | Явно объявлено вне Release 1.0 (`TEN-092`) с обоснованием; общий бэкап и PITR сохраняются |
| RA-04 | Дисциплина денормализации scope | **Средний** | Новая сущность, добавленная без scope-колонок и composite FK, обходит изоляцию | Приложение M как единый реестр; DoD пункт 3a; архитектурные тесты `TEST-SEC-021`, `TEST-SEC-022`; тест `TEST-TEN-040` на уровне БД |
| RA-05 | Отсутствие RLS | **Низкий** | Дефект в handler'е, обошедший и Global Query Filter, и явную проверку, не будет остановлен базой при чтении | Композитные FK защищают **запись**; чтение защищено двумя независимыми уровнями приложения плюс архитектурными тестами. RLS вынесен в hardening (`TEN-031`) |
| RA-06 | Сложность frontend-состояния филиала | **Низкий** | Незакрытый диалог или неотменённый запрос показывает данные прежнего филиала | Обязательная последовательность из 6 шагов (`FE-037`), запрет показа данных прежнего филиала (`FE-038`), тест `TEST-TEN-035` |
| RA-07 | Email не переиспользуется между организациями | **Низкий** | Сотрудник, работающий в двух организациях, обязан иметь два разных адреса | Осознанное следствие глобальной уникальности (`TEN-028`); альтернатива потребовала бы переписывания формы входа |
| RA-08 | Миграция prototype-БД требует ручного разбора | **Средний** | Рассогласованные данные не могут быть исправлены автоматически; ошибка разбора создаёт утечку | Pre-migration validation query, запрет автоматического исправления (`TEN-084`), обязательный backup, обратимость этапов 1–3 |
| RA-09 | Организация или филиал без администратора | **Низкий** | Деактивация последнего администратора оставляет контур без управления | Допустимое, но наблюдаемое состояние: уведомление `BranchWithoutAdmin`, метрика `users_total{role,admin_scope,branch}`, алерт «Филиал без администратора» дольше 24 часов |
| RA-10 | Рост объёма документа | **Низкий** | 5416 строк трудно поддерживать вручную; риск расхождения при правках | Единые источники истины: Приложение A (права), M (scope и ограничения), N (эндпоинты), L (значения), раздел 38 (арендная модель), раздел 13 (автомат); правила приоритета при расхождении зафиксированы явно |

Ни один остаточный риск не блокирует начало разработки. Риски RA-01, RA-02 и RA-03 являются прямыми следствиями выбранной модели shared database и зафиксированы в ADR-001 как принятые отрицательные последствия.
